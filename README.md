1.2.31 补充 MAKCU 连接期的只读设备诊断：先确认 V4 路由响应，再读取固件版本及插值设置；仅查询，不修改固件、插值、鼠标屏蔽或移动方式。查询后重新验证文本握手，防止诊断残余回包干扰移动确认。原生控制器沿用 1.2.30；针对手动移动和人物变向的预测候选在扩大测试中出现退步，均未部署。设备回包耗时不能替代物理执行测量。调查及完整反例见 `audit/manual-motion-20261019/RESULTS.md`。

1.2.30 修复已确认停止相对运动后，六帧速度拟合仍携带旧速度的问题：最近四帧在所有候选 HID 执行延迟下均支持接近零速时，及时清除旧速度。持续运动仍使用原六帧拟合，未缩短换人等待。更激进的短窗口反向预测因噪声/延迟波动测试退步已撤回。新增 `confirmed_stop_velocity_resets_x/y` 计数区分真实触发与主观推测；该修复仅改善局部急停情形，不代表复杂实战已达到零延迟、零误差。离线对照及部署证据见 `audit/follow-response-20261019/RESULTS.md`。

1.2.29 修复多人仍然可见时，置信度跨过高低分组阈值造成的身份错配：高分优先、低分随后匹配可能使两条旧轨迹争抢同一个低分框，把原编号交给邻人，并为另一个仍可见人物重建编号。现在仅对完整、新鲜、逐对强匹配且人物框不过度重叠的集合，联合匹配已有身份；缺人、严重重叠、过旧观察和弱几何继续沿用原有约束，低分框仍不能创建新身份。目标切换确认、保留时长、运动增益与校准保持原设置。该修复没有引入人物外观识别，不能解决完全重叠后的身份歧义。根因复现、未采用方案、独立序列与部署证据见 `audit/identity-root-cause-20261019/RESULTS.md`。

1.2.28 修复多人重新选人时的反复确认：旧锁已失效时，继续确认已选中的合格人物，避免每帧分数排名变化反复重置确认。人物消失、低于新目标置信度门槛或关联不再匹配时仍重新选择并完整确认。此前 1.2.27 尝试在原身份保留期内预先累计邻人确认，用户反馈“开始更快，但换人跳变增加”，该优化已撤回。当前保留 1.2.26 的普通 350 ms / 已知邻人竞争时 500 ms 身份保留期，以及其后完整的换人确认；跟随增益与输出链路不变。证据、被拒绝的候选及适用边界见 `audit/crowd-acquisition-20261019/RESULTS.md`。

1.2.26 针对多人场景中原人物短暂遮挡后被邻人接管的问题：存在已知邻人时，控制层等待跟踪器对原身份的 500 ms 保留期结束，再允许确认换人；邻人间歇漏检不会缩短已开始的等待。陌生新目标沿用普通 350 ms 保留期；始终不可见时不发送盲目移动。旧锁定过期后的重新选择也继续遵守新目标置信度门槛，避免低分邻人绕过检查；原人物的低分连续观测仍保留。代价是原人物确实消失时，切到已知邻人最多多等约 150 ms。没有改动已锁定人物的运动增益。证据及被拒绝的候选见 `audit/multi-target-lock-20261019/RESULTS.md`；这不解决仅靠几何无法区分的完全重叠身份问题。

1.2.25 修复 Host 重开或重新开始传输后，手机可能一直拒收新画面的问题。Host 固定使用 UDP 5002，但帧编号从头计数；接收端现在同时检查连续帧编号倒退的证据，在旧序列停止前进至少 300 ms、新序列连续推进至少 50 ms 且至少四个不同帧后重建解码会话，并请求完整关键帧。单个乱序包、重复分片、重复画面标记和正常编号回绕不会单独触发重连。这个判断是兼容现有协议的恢复启发式，不是显式会话编号；测试范围、部署状态和限制见 `audit/connection-recovery-20261019/RESULTS.md`。控制器沿用 1.2.24。

1.2.24 修复跟踪编号重建后无法及时恢复跟随的问题：新编号第一帧没有通过几何检查，不再立即被永久归类为旁边的人；与原目标同时可见的其他编号仍禁止直接接管锁定。恢复时继续要求唯一候选、严格重叠/距离、置信度和体型检查，保持原控制编号和指令节奏。13 组既有动态场景结果相同；72 组额外延迟压力场景中，9 组原本持续丢失的情景得到恢复，同时有 4 组误差退化，详见 `audit/lock-recovery-20261019/RESULTS.md`。这些是合成结果，不是实战命中率；多人完全重叠仍缺少外观身份依据。

1.2.23 修复视频接收端将短暂缺帧放大为推理长时间中断的问题：完整 IDR 关键帧可以越过已缺失的参考帧；丢帧、拒收预测帧或请求关键帧时保留其他正在拼接的帧；按逻辑帧序淘汰旧帧，避免乱序包挤掉正在接收的新关键帧。普通预测帧继续严格遵守解码顺序和参考链保护。发送端仍有数据时，关键帧重试保持至多每 500 ms 一次；完全静默时保留退避与重试次数上限。控制器、校准和目标选择沿用 1.2.22。本轮故障证据、测试及真实部署情况见 `audit/inference-interruption-20261019/RESULTS.md`。

1.2.22 针对“先跳到人物附近、停一下再补到身上”的初次锁定过程：第一步也使用已经测得的画面间隔，避免在 120–140 FPS 下仍按 60 Hz 计算一次过大的初始移动。后续追赶、目标归属和校准逻辑沿用 1.2.21。81 组延迟/灵敏度/帧率合成组合中，48 组最大单步跳动减少，没有增加的组合；收敛时间中位变化为 0，最大增加 16.7 ms。连续追赶与形变回归未退步。另一个逐条指令延迟不一致的速度估计缺口已复现，但修正候选损害部分追赶场景，未部署。详见 `audit/response-jitter-20261019/RESULTS.md`。

1.2.21 修复三个身份/运动连续性问题：尺寸阈值的浮点误差、临时大框继续影响下一帧关联，以及框恢复正常后生成虚假速度。轨迹保留时长与速度预测时长分开；完整且可信的可见目标集合采用全局一对一关联，低分框保留与可见人物优先规则继续有效。研究、拒绝的候选、合成测试和实机证据见 `audit/research-tracking-20261019`。合成场景收益不等于全部实战场景已经解决；完全重叠或强遮挡下的身份仍缺少外观证据。

1.2.20 修复检测框突然伸缩后，瞄点跳跃和旧速度历史继续制造反向指令的问题。突变尺寸观察一帧，两侧边缘共同支持的平移立即跟随；新尺寸连续出现后采用。身份预测使用同一份已确认的控制几何，较大几何修正不继续当作持续速度。原 1.2.19 的追赶增益和响应校准保留。新增遮挡、变形与移动的闭环对比，并记录 `tracker_control_extent_confirmations`、`body_shape_motion_resets` 和逐帧 flags 8192。最复杂合成场景仍有较大误差，不能称作所有英雄均已稳定。见 [运动完整性审计](audit/motion-integrity-20261019/MOTION-AUDIT.md)。

1.2.19 针对“抖动减少但跟随变慢”：在输出延迟估计连续稳定两个响应周期、目标仍向远离准星的方向运动时，逐渐增强位置反馈；近目标、转向、观察中断或延迟变化时恢复基础反馈。速度预测不额外放大。分离自身鼠标运动时，同时保留原校准与当前估计的可能执行时间范围，避免过早排除仍可能发生的延迟。逐帧 flags 位 2048/4096 与 `pursuit_boosted_x/y_frames` 记录增益启用；它们不表示物理移动或命中。验证与限制见 [跟随响应审计](audit/responsive-pursuit-20261019/PURSUIT-AUDIT.md)。

1.2.18 修复同一人物持续可见时，速度估计在不同坐标参考之间切换而产生反向输出的问题。执行时刻不确定时，扣除相机运动得到的目标速度必须先通过屏幕相对运动区间约束；观察不足时继续位置反馈，暂不叠加没有依据的速度预测。四个方向的单人回归从最大 9 个错误反向计数降至 0，保留原响应增益、校准、目标选择及输出接口。逐帧 flags 位 512/1024 与 `retinal_velocity_constraints_x/y` 记录两轴约束，不能直接当作物理命中或锁定率。见 [同人抖动审计](audit/same-target-jitter-20261019/JITTER-AUDIT.md)。

1.2.17 修复已消失轨迹从持续可见邻人手中抢走识别框的问题：旧编号被错误恢复后，会绕过换人确认。现在先解决通过原有几何和歧义检查的可见轨迹延续，再恢复丢失轨迹；原目标独立返回仍可恢复。新增 1,728 组连续序列中，432 组改善，未发现身份匹配退步；交叉同类人物仍有未解决的身份歧义，构造用例不是实战锁定率。证据和部署记录见 [可见轨迹优先审计](audit/active-track-priority-20261018/ACTIVE-TRACK-AUDIT.md)。

1.2.16 修复不同体型人物重叠时，已知邻人的框阻止原人物匹配、使仍可见目标进入等待的问题。只有与另一条新鲜可见轨迹强重叠、尺寸一致的框才可解除这类冲突；缺乏明确归属的尺寸突变仍保留防换人限制。手机独立控制测试已复现修复前的错误等待，并验证修复后继续追向当前目标位置。整套回归和上一版 70,884 个身份用例没有退步，尚不能代替实战验收。依据见 [人物归属冲突审计](audit/association-ownership-20261018/OWNERSHIP-AUDIT.md)。

1.2.15 修复背景运动估计不可用时，整组人物随视角移动会把旧锁定编号交给旁人的错误。只有相邻画面的整组人物可以一致对应时才校正身份参考；人数不完整、独立运动或间隔过长时不采用这项校正。它不充当相机运动测量，也不修改鼠标比例。48 项原生测试、45 项 Java 自测、既有动态场景和额外 40 组压力测试已通过；由录制检测框构造的 70,884 个身份用例未出现新增回归，但不能代替实战身份标注和效果验收。证据见 [本轮身份连续性审计](audit/identity-continuity-20261018/IDENTITY-AUDIT.md)。

1.2.14 修复短暂丢失后首次可见指令被放大，以及同人编号重建后重复执行初始追赶的问题，记录见 `audit/motion-relative-20261018/CONTROL-CONTINUITY-AUDIT.md`。1.2.13 的控制链路审计保留在 `audit/full-control-20261018/CODE-AUDIT.md`；此前被拒绝的候选不能当作当前版本结论。

## 使用

1. 手机安装 `dist/VisionForge-Local.apk`，电脑运行配套 `dist/VFHost-Local.exe`。
2. 两端接入同一局域网或原有 CAT6 直连链路，打开手机 VF，再开始电脑端传输。
3. 选择已经连接的 USB MAKCU 或蓝牙 HID 输出。蓝牙路线还使用电脑传来的鼠标按钮状态。
4. 触发选项包括右键、两个侧键及“始终开启”。“始终开启”不需要按住鼠标键，但仍要求链路、推理和输出设备健康。
5. 手机退到后台、退出、停止传输或设备断开时关闭控制输出；返回前台后重新准备链路。通知提供“停止”操作。

请使用这里成套的 Host 和 APK。设备权限、网络检查、指令期限、停止取消与断线保护仍有效。

## 当前 Overwatch 模型

候选安装包只包含 **Overwatch YOLO11m 640，QNN HTP v75 W8A16** 模型，单输入640×640、8400候选、单类身体检测。来源是用户压缩包的 `yang0828_v11m_640.onnx`；原始模型、分离输出图与所选QNN库的哈希记录在 `models/overwatch/production.json`。量化校准与数值验证使用不同录像。没有独立头部网络。

默认“头部估计”使用身体检测框顶部向下18%的瞄点；“检测框中心”保留供手动选择。原416偏好与MAKCU/蓝牙各自校准记录保留；迁移到640模型时保留物理屏幕位移含义和原测量日期。现用同设备、同路线参考最长保留30天；修改游戏灵敏度/DPI等会使原比例不再适用。

浮点参考图位于 `models/overwatch/ow_m_640/split.onnx`，手机实际加载 `libow_m_640_w8a16.so`。安装包仅包含当前NPU图，没有打包CPU/NNAPI后备图。其余精度实验独立归档，未经数值与实机验证不会替换生产模型。

## 这次稳定性与延迟修复

- 当前 NVIDIA 小尺寸采集使用经过负载测试的 GPU 上下文优先级；64–640 像素场景自动选用 CPU Media Foundation H.264，避开游戏满载时已测得的 NVENC 等待。大画面和显式选择 NVENC 的路径保留。
- 修正 Media Foundation 强制关键帧参数类型，恢复连接后可及时重新解码；相同网络仍在线时不再反复取消三秒左右的 QNN 初始化。
- Host 队列中重复帧不再覆盖待处理的新画面；静止画面的重复发送限制为 30 Hz，新画面不受该限制。
- 解码器合并已就绪输出，保留最新画面；过旧帧在预处理前丢弃，防止旧帧积压。合并时保留新画面标记。
- 预处理缓存缩放坐标，减少逐像素计算；固定输入大小走专用路径。
- 蓝牙 HID 调用移到有界发送线程，指令带有效期和代次；松键、停止、恢复或断线后的旧指令不能重新生效。
- 修复控制开关状态被旧健康快照覆盖的问题，尤其是侧键按住时叠加左键的场景。
- 日志异步写入，避免逐条同步刷盘阻塞推理/控制；区分蓝牙 API 接受、USB 写入与真正的设备反馈。
- Android 16 以太网请求权限问题及 QNN 卸载相关崩溃已修复，历史诊断见 `audit/overwatch/CRASH-FIX.md`。

当前控制器持续处理新观察，结合图像背景位移、目标移动趋势和已被输出接口接受但尚未预计出现在画面中的移动。响应系数和延迟通过短窗相关性估计，估计不是物理回执。未知响应时限制输出；检测位置的短时线性趋势不连贯时不进行速度外推，减少把检测框噪声放大成鼠标抖动。目标暂时漏检时通常保留身份 350 ms；候选中出现已知邻人时，等待延长至跟踪器的 500 ms 保留期，且邻人间歇漏检不会提前结束等待。身体目标短暂不可见时保留身份并暂停盲目输出；切换目标还需新的确认。此保留窗口会增加旧目标真正消失后切到新目标的等待。

1.2.7 修复了实测日志复现的限幅错误：旧指令退出窗口后，剩余有符号总量可能超出预算，旧夹取表达式会把零输出强制变成反向移动。现在限幅只能减小或抑制原请求，不能制造、反转或放大移动；估计中的待执行移动也不能单独触发反向拉回。横纵轴分别处理，避免横向达到限幅时纵向一起暂停。

1.2.9开始保存同设备、同模型、同输出路线的响应校准；当时的24小时期限已在本轮调整为30天，并继续保留原测量日期。恢复后的响应比例固定，后续画面相关性只更新吻合范围内的延迟估计，避免复杂画面把纵轴比例从约 0.75 错估为 0.27 后放大鼠标输出。安装升级、控制开关和同路线配置重载保留校准；改变路线或模型不会混用。缓存位于手机诊断目录 `control-response-模型-路线.json`。改变游戏灵敏度后旧比例不再适用，需移除对应缓存并重新校准。

1.2.10 增加可变指令延迟的闭环回归：原来单个静止目标也会在 FIFO 延迟波动下持续振荡。推算运动需在更宽的延迟区间内同向，无法确认时保留独立图像测得的目标趋势；不会把模型不确定误写为目标静止。单人场景中，稳定的同一跟踪编号允许更大的镜头位移；新编号仍需较强几何重叠才能继承锁定。自动测试不能证明实际所有英雄、多人交叉、镜头移动及技能场景均已稳定。

1.2.13 为每轴速度增加有效性标志，区分“测得相对静止”和“当前无法判断”，防止玩家已跟住目标时又叠加背景补偿速度。连续身体观察允许保留足够可见的部分出画框，瞄点限制在可见区域。生产预测上限显式设为 48px，未来点和边界一起推进；这不等于未来位置一定准确。MAKCU 保留 4 Mbps USB 异步读取修复，蓝牙路线继续可用。校准记录保留原始校准时间和来源，单纯更新延迟不再延长旧比例有效期。

## 日志和验证

手机日志：`/sdcard/Android/data/com.visionforge.mobile.local/files/diagnostics/visionforge-mobile-runtime.jsonl`，每个文件32MiB，总计最多16段。日志带 UTC、单调时钟、进程、线程和追踪编号；持续记录链路、推理、控制阻断原因、发送间隔、队列和热状态。逐帧 `control_trace_v6` 保留原有身份、位置、背景、速度、待执行位移、传输帧编号、框及置信度，并记录候选竞争、切换确认、速度有效性与控制分量。`detection_trace_v1` 保存每帧最多 16 个检测框及总数，超出时明确标记，支持离线复查；`dispatch_trace_v1` 和 `delivery_trace_v1` 使用票据关联派发和完成；`runtime_clock_anchor` 对齐 Android 两种时钟。固件回包和 Android API 返回均不等于物理执行。追踪按完整样本分块写入，不在界面刷新时构造长日志。电脑日志：`%LOCALAPPDATA%/VisionForge/DualMachineLocal`，性能 CSV 版本为 **v9**，包含前台进程 ID，用于辨别游戏负载测试是否有效。

Host 支持按需记录现有编码的游戏裁剪流：启动进程前显式设置 `VF_DIAGNOSTIC_CLIP_DIR` 和 `VF_DIAGNOSTIC_GAME_PID`，只在指定游戏处于前台时记录，60 秒或 64 MiB 即停止，切出游戏也停止。默认不开启，不增加屏幕采集或编码实例；写盘在独立线程。片段、原始逐帧日志和个人缓存不进入源码包。

当前验证与文件哈希见 `audit/verification.json`；本轮恢复与后续优化证据见 `audit/restore-body-head-20261019/RESULTS.md`。此前实测见 `audit/inference-interruption-20261019/RESULTS.md`、`audit/response-jitter-20261019/RESULTS.md`、`audit/research-tracking-20261019/RESULTS.md`。`audit/live-20261018/RESULTS.md`、`audit/control-20261018/RESULTS.md` 和其中的真机视频回放是早期版本证据，未重新绑定当前控制实现。素材不能证明覆盖全部英雄或提供完整识别准确率。`host_plus_receive_to_result` 包括电脑采集/编码发布年龄和手机接收后的处理，**不包括未知单程传输时间**，也不包括蓝牙、游戏接收和渲染，不能称为完整端到端延迟。

`VisionForgeRawMouseProbe` 是按需运行的电脑只读诊断工具，最多运行 120 秒，使用隐藏消息窗口记录鼠标移动到达 Windows 的时间和匿名设备序号；不记录键盘、设备地址或修改输入。配合 `scripts/measure-phone-clock.py` 和 `scripts/analyze-hid-arrivals.py` 可分析发送与接收的对应关系。时间结果需要带上对时误差；重复小幅移动的匹配只是相关性证据，不能替代外部硬件延迟测量。该工具不随 Host 常驻运行。

## 构建

工具：JDK 17、Android SDK 35、NDK 27.0.12077973、CMake 3.22.1、Visual Studio 2022 C++ Build Tools。QNN 头文件在 `vendor/qnn/include`。

```bat
scripts\build-host.bat
scripts\build-android.bat --offline
python scripts\test-java.py
scripts\build-native-target.bat all
"%ANDROID_HOME%\cmake\3.22.1\bin\ctest.exe" --test-dir build/host --output-on-failure > audit/native-tests-current.log
python scripts\evaluate-control-dynamics.py --run-candidate --baseline audit/responsive-pursuit-20261019/final-servo.log --shape-baseline audit/motion-integrity-20261019/baseline-shape.log --candidate audit/servo-current.log --output audit/dynamic-current.json
python scripts\verify-local.py --device 实际IP:调试端口 --live-collection 本次诊断目录 --native-log audit/native-tests-current.log --dynamic-report audit/dynamic-current.json --model-report audit/model640-20261022/model-validation.json --pipeline-report audit/model640-20261022/pipeline-validation.json
```

首次准备构建依赖可能需要网络。Host 产物为 `build/host/VFHost.exe`；APK 位于 `android_inference_benchmark/app/build/outputs/apk/release/app-release.apk`。本地 APK 使用开发签名，没有生产发布密钥。

真机测试入口位于 `android_inference_benchmark/app/src/androidTest`，电脑端回放脚本为 `scripts/test-video-replay.py`。测试 APK 不需要交付给日常使用者。普通测试用 `scripts\build-android.bat --offline :app:assembleReleaseAndroidTest` 构建，回放时保持 VF 前台；退出前台会正常停止链路并被记录为中断。独立进程测试构建时追加 `-PheadlessBenchmark`，脚本加 `--headless`，切换应用不会因为 Activity 生命周期停止计算，但后台无线性能不保证与前台一致，不能清理 VF 后台。追加 `--device-local` 会上传测试输入并在手机内部回放，用于隔离无线因素；追加 `--foreground-activity` 会显示 VF 并暂停其常规管线，让独立测试拥有接收端。两种测试 APK 的目标进程不同，需要安装与模式对应的测试 APK；测试前停止电脑 Host，避免两个视频发送端争用链路。
